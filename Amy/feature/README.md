# Blind Spot Investigator: data pipeline

These scripts build the data behind the dashboard in `Amy/frontend/`. They take the team's final model's **historical** rankings, find the 43 confirmed exploits (KEV additions) that ranked below the review line of 517, gather the evidence for each one, and attach AI-written explanations and advice.

The pipeline is **read-only** toward everything outside `Amy/feature/output/`:

- It does not train, refit or change any prediction model.
- It reads the team's saved results in `chen/` and the original IBM CSVs in `data/`, but never writes to them.
- Every result is historical (2024–2025 CVEs). Nothing here predicts 2026 exploitation.

## Pipeline

Run every command from the repository root. The steps are listed in order; each one reads the files written by the steps before it.

| Step | Script | Reads | Writes to `output/` |
| --- | --- | --- | --- |
| 1 | `build_blind_spots.py` | The team's out-of-fold scores (`chen/results/cv_oof_lr.parquet`, `cv_oof_lora.parquet`) and `data/vulnerabilities.csv`, `known_exploited.csv` | `historical_rankings.csv`, `blind_spots.csv`, `summary.json` |
| 2 | `prepare_investigations.py` | Step 1 outputs and the IBM CSVs | `investigation_cases.json` |
| 3 | `analyze_blind_spots.py` | Steps 1–2, `chen/processed/cv_folds.parquet` and the monthly exploit-signal CSVs | `disagreement_analysis.json`, `blind_spot_case_studies.json` |
| 4 | `build_explanation_evidence.py` | Steps 1–3, the team's saved logistic regression weights and feature code in `chen/` | `explanation_evidence.json` |
| 5 | `watson_explain_misses.py` | `explanation_evidence.json` and IBM watsonx.ai | `watson_miss_explanations.json` |
| 5b | `apply_offline_investigations.py` | `offline_investigations.json` | Merges into `watson_miss_explanations.json` |
| 6 | `build_dashboard_data.py` | `watson_miss_explanations.json`, `explanation_evidence.json` | `dashboard_investigations.json` (the dashboard's only input) |

Step 1 stops if it cannot reproduce the team's documented result of 32 caught and 43 missed. Step 4 checks its rebuilt linear-model scores against the team's original scores before using them.

Steps 2 and 3 also write a few side files: `investigation_cases.csv`, `investigation_summary.json`, `watchlist_evaluation.csv` and `research_findings.md`. Nothing downstream reads them, so they were deleted. Rerunning those steps recreates them, and they can be deleted again.

### Commands

```powershell
python Amy/feature/build_blind_spots.py
python Amy/feature/prepare_investigations.py
python Amy/feature/analyze_blind_spots.py
python Amy/feature/build_explanation_evidence.py
python Amy/feature/build_dashboard_data.py
```

Steps 1 and 2 look for the IBM CSVs in `data/` and similar folders. Pass `--data-dir <folder>` if they are somewhere else.

## The investigations are complete. Don't regenerate them

`watson_miss_explanations.json` holds the finished, validated investigation for the cohort and all 43 misses. **Do not rerun step 5 or 5b.** The records must stay as they are so their provenance stays accurate. `build_dashboard_data.py` stores the file's SHA-256 hash in `dashboard_investigations.json`, so any change is detectable.

| Source of the AI text | Records |
| --- | ---: |
| Generated by IBM watsonx.ai (`ibm/granite-4-h-small`) | 29 |
| Written offline by the Cursor agent from the same evidence packets, not by watsonx.ai | 9 |
| watsonx.ai draft, corrected offline by the Cursor agent to pass the validator | 6 |

The offline records came from `offline_investigations.json`, merged by `apply_offline_investigations.py`. Both files are kept as the record of where that text came from. Every record, whatever its source, passed the same automatic checks, and its source is shown on the dashboard.

Only step 6 is safe to rerun. It makes no AI calls and reads the investigation records without changing them.

## Verified facts versus AI text

Each investigation keeps two parts separate:

- **Verified evidence**, calculated by code: the rank from each model, exploit signals in the month the CVE was scored, the linear model's per-feature contributions, missing information, and how similar CVEs turned out.
- **AI analysis**: possible explanations and analyst advice. Each claim must cite named evidence, and the validator rejects claims that don't match it. Confidence is capped at medium. These are hypotheses, not proven causes.

A CVE with no exploit-signal record is treated as **unknown**, not as "no exploit". The model stored those flags as zero, and the dashboard points this out.

## Output files

| File | Contents |
| --- | --- |
| `historical_rankings.csv` | All 75,148 historical CVEs with each model's score, the ensemble rank and the KEV outcome |
| `blind_spots.csv` | The 43 misses |
| `summary.json` | Headline counts for the evaluation |
| `investigation_cases.json` | All 75 KEV positives with signals, NVD context and outcome |
| `disagreement_analysis.json` | Test of whether model disagreement finds misses (it did not beat reviewing further down the ranking) |
| `blind_spot_case_studies.json` | Tagged example cases |
| `explanation_evidence.json` | Per-CVE evidence packets used for the investigations |
| `watson_miss_explanations.json` | **Final investigation records. Do not overwrite.** |
| `dashboard_investigations.json` | Trimmed, display-ready version for the dashboard |

## Environment

- **Data steps (1–4, 6):** Python 3.10+ with `pandas`, `numpy`, `scipy` and `pyarrow`.
- **watsonx.ai steps (5, 5b):** the git-ignored virtual environment `Amy/feature/.venv`, which has `ibm-watsonx-ai`. Credentials are read from the git-ignored `Amy/feature/.env` and are never printed or written to output. Don't commit, share or open that file.

## Limitations

- The 75 KEV positives are confirmed exploits, not a representative sample of all CVEs. The caught-versus-missed comparison is descriptive, not causal.
- Only the logistic regression model exposes per-feature effects. Granite LoRA and LightGBM report ranks only.
- NVD descriptions and scores are current versions and may have been edited after the CVE was scored.
- KEV is a list of confirmed exploitation. A CVE missing from it is not proof that it was never exploited.
